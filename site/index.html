A prompt-driven agent on an Android phone, with a Node runtime, a shell, a filesystem and a memory store. This page is not a portfolio of screenshots — it is built from the same techniques it describes, and every number is computed live in your browser.

What this agent actually is

Three things, and nothing mystical. It is a markdown file that becomes the system prompt, a set of MCP servers that give it hands, and an append-only store it can write to.

PROMPT.md — the system prompt. plain markdown.
agent.json — model, endpoint, list of MCP servers
memory/memories.jsonl — append-only. one op per line.
termux-mcp/
  termux-mcp.js — shell_exec
  memory-mcp.js — memory store
  session-mcp.js — session_brief, built this session
  termux-api-mcp.js — 21 Termux:API commands, built this session
daemon/
  scheduler.mjs — cron scheduler, per-job locks
  install-android-job.sh — survives Android killing Termux
  jobs.mjs — builtin jobs, all ship disabled
Prompt
A markdown file, not code. Edit the file, restart, the persona changed.
Hands
MCP servers over stdio. Each one is a process the agent can call.
Memory
JSONL. Every write appends; nothing rewrites. Trivially auditable.
Model
Configurable. Runs wherever a completion endpoint exists. (One lives on a phone, sitting in a drawer.)
Failure
Bounded everywhere. Every external call is timeouted and killed on expiry.

Scheduling and unattended work

Jobs are defined in JSON, fire on a cron schedule, and take a lock so two schedulers cannot run the same job twice. Android can hand a job back after the app is killed, which is the only way this survives on a phone.

daemon/jobs.json — user jobs. shadows a builtin of the same name.
  { "name": "nightly", "kind": "llm", "enabled": true,
    "schedule": "0 3 * * *", "prompt": "…" }

Every job ships disabled. turn one on deliberately.

two schedulers, because they fail differently:
· resident scheduler — 1 min granularity, dies when Android reclaims Termux
· Android job — 15 min floor, survives reboot

Limits, stated plainly

A capabilities page that omits the failure modes is marketing. These are the real ones, current as of today.

Termux:API is installed but does not answer. The broadcast is delivered (am broadcast returns 0) and the app is alive, but the reply never arrives, so every call blocks. Root cause narrowed to a Binder back-channel that is never answered. Raised timeouts will not fix it. Higher timeouts are not the answer; the reply does not exist. We built a timeouted MCP server specifically so this failure is bounded rather than session-ending.
Blocked
Termux:API (21 commands) and Android JobScheduler — the same dead bridge blocks both.
Blocked
Camera, microphone, SMS, contacts, call log. Not in the catalog on purpose.
Broken
A plaintext API key sits in four config files. Contained (gitignored, untracked) but unrotated. The daemon redacts it from logs, but redaction is not rotation.
Structural
Structured tools are sandboxed to one directory; shell_exec is not. The safety property is decorative.
Missing
No continuity between sessions beyond memory search. No introspective access to its own inference config. Cannot see or set Android jobs without going through a bridge.
